# Toret community API, v1

The one contract the Swift client and the Go Lambda both implement. The
machine-readable twin is [`openapi.yaml`](openapi.yaml); where the two disagree,
this file wins and the YAML is the bug.

- Base URL: `https://torino.deepdive.dev.br`, every route under `/v1`.
- Transport: API Gateway HTTP API (payload format 2.0) in front of one Go Lambda
  for the routes, and a second scheduled Lambda that fills the weather and SMAT
  caches. No CDN in front, so the source IP API Gateway reports is the real one.
- Format: JSON, UTF-8, `Content-Type: application/json; charset=utf-8` both ways.
- No accounts. A write is attributable to an install token, never to a person.

## 1. Honesty rule, as it applies to the wire

The app has no live per-fountain water data. Only a dated user report may ever
make the app say a fountain is running or dry, and only for 36 hours
(`CommunitySummary.freshness`). Therefore:

- Weather and SMAT works notices are **context**. They carry their source and a
  `fetchedAt`, and they never carry a field named or worded like a water state
  (`status`, `dry`, `off`, `running`, `available`). A server must not add one.
- The server sends **structured fields only**. The sentence the app shows ("SMAT
  lists a works order near <street>, started <date>. Supply nearby may be
  affected.") is built and localised in the app (pt-BR, en, it).
- Summaries are a hint for cold start, pins and widgets, not the truth
  (section 6.3).

## 2. Conventions

### 2.1 Versioning

The version is the first path segment. Within `/v1` the server only **adds**
things: new optional response fields, new endpoints. Clients ignore unknown
fields. Breaking changes ship as `/v2` and `/v1` stays up until the oldest
supported app no longer uses it.

**Enums are closed in v1.** The server may emit only the values listed here.
`WaterState` and `ReportTag` are Swift enums decoded with the synthesized
`Decodable`, so one unknown value fails the whole list on an old client. Adding
a value is a `/v2` change.

### 2.2 Request headers

| Header | Where | Meaning |
| --- | --- | --- |
| `X-Toret-Install` | required on `POST`/`DELETE`; ignored on `GET` | The install token, section 7. 16 to 64 characters from `[A-Za-z0-9._-]`. Used byte for byte: no case folding, no trimming. Missing or malformed: `401 install_required`. |
| `X-Toret-Client` | optional, always sent by the app | `<version>+<build>`, e.g. `1.0.0+42`. Logged only. Reserved for a `426 upgrade_required` kill switch (`MIN_CLIENT` env on the Lambda, unset in v1). |
| `Accept-Language` | optional | Only picks the language of the developer-facing `error.message` (`pt`, `en`, `it`; default `en`). No user-facing text is produced by the server. |
| `Content-Type` | required on bodies | `application/json`; anything else is `415 unsupported_media_type`. |
| `If-None-Match` | optional on list `GET`s | Section 5. |

`GET` responses never depend on the install header, so one ETag is shared by
every client (the only `Vary` is `Accept-Encoding`, section 5).

### 2.3 Value formats

- **Timestamps** are RFC 3339 in UTC at whole-second precision: `2026-10-12T09:41:00Z`.
  Swift's `.iso8601` decoding strategy (used by `FilePersistence` and to be used
  by the HTTP backend) **rejects fractional seconds**, and Go's default
  `time.Time` marshalling emits nanoseconds. The Go side formats with
  `t.UTC().Truncate(time.Second).Format(time.RFC3339)` and parses requests
  leniently (fractions and numeric offsets accepted, then normalised).
- **Calendar dates** (`startedOn`, `plannedEnd`) are plain `YYYY-MM-DD` strings
  in Europe/Rome, not timestamps.
- **Fountain ids** are OSM node ids as strings (`"421310659"`), as in
  `Shared/Resources/fountains.json`.
- **Report ids** are UUIDs, generated by the client (`UUID().uuidString`, upper
  case). The server accepts any case, stores and returns **upper case**.
- Absent optional values are omitted (Swift's encoder does the same). Clients
  and servers accept `null` as equivalent to absent.

## 3. Errors

Every non-2xx response produced by the Lambda has this body:

```json
{ "error": { "code": "invalid_note", "message": "Note contains a link, address or phone number.",
             "field": "note", "reason": "contains_contact", "requestId": "c6af9ac0-7b8d-4f2e-bf08-1e0c1f3a2b11" } }
```

`code` is the stable, machine-readable part. `field` and `reason` are present
for validation errors. `message` is for logs, never shown to users.
`requestId` is the API Gateway request id, also returned as `X-Request-Id`.

Two responses are produced by API Gateway itself and do **not** have this body:
`404 {"message":"Not Found"}` for an unknown route and `429
{"message":"Too Many Requests"}` when the stage throttle trips. Clients key on
the status code, not the body, and treat a 429 without `Retry-After` as 60 s.

### 3.1 Status codes

| Status | `code` | When |
| --- | --- | --- |
| 200 / 201 / 204 | | Success. |
| 304 | | `If-None-Match` matched (no body). |
| 400 | `bad_request`, `invalid_limit` | Malformed JSON, bad query parameter, bad path id. |
| 401 | `install_required` | Missing or malformed `X-Toret-Install` on a write. |
| 403 | `not_owner`, `forbidden` | Delete by a different install; banned install (on any write). |
| 404 | `unknown_fountain` | `GET /v1/fountains/{id}/reports` with an id not in the catalogue. |
| 409 | `id_conflict` | Report id already stored by a different install. |
| 413 | `body_too_large` | Body over 4 KiB. |
| 415 | `unsupported_media_type` | |
| 422 | `empty_report`, `unknown_fountain`, `invalid_id`, `invalid_state`, `invalid_rating`, `invalid_tags`, `invalid_note`, `invalid_date`, `invalid_reason` | Well-formed JSON that breaks a rule in section 6.4. |
| 426 | `upgrade_required` | Reserved. |
| 429 | `rate_limited` | Section 4. Always with `Retry-After`. |
| 500 | `internal` | Bug. |
| 503 | `unavailable` | DynamoDB throttling or an upstream dependency down. `Retry-After` set. |

### 3.2 What the client does with an error

`Community.flush()` stops at the first failure and keeps the queue in order, so a
**permanent** error left in the queue would block every later upload forever.
The HTTP backend therefore splits errors in two:

- **Retryable**: network errors, timeouts, `408`, `429`, any `5xx`. The item
  stays queued; for `429`/`503` wait at least `Retry-After` seconds.
- **Permanent**: every other `4xx`. The backend treats the call as done (so
  `flush` removes the item from the queue) and, for a save, surfaces the matching
  `SubmitRejection` if it can:

| Server | Client |
| --- | --- |
| `422 empty_report` | `.empty` |
| `422 invalid_note`, `reason: objectionable` | `.objectionable` |
| `422 invalid_note`, `reason: contains_contact` | `.containsContact` |
| `429 rate_limited` on `POST /v1/reports` | `.rateLimited(minutesLeft: ceil(Retry-After / 60))` (retryable, stays queued) |
| anything else permanent | dropped silently |

The app filters before it sends, so these should only fire for a modified
client or a filter that drifted. `403 forbidden` (banned install) is dropped
the same way.

## 4. Limits, rate limits and size caps

| Limit | Value | Over it |
| --- | --- | --- |
| Request body | 4 KiB (checked on the byte length before parsing) | `413` |
| `X-Toret-Install` | 16 to 64 characters | `401` |
| Note | UI limit 140 characters (`Report.maximumNoteLength`). Server cap: at most **280 Unicode code points** after trimming | `422 invalid_note`, `reason: too_long` |
| Tags | at most 3, unique | `422 invalid_tags` |
| Writes per install | 40 per clock hour (`POST`, `DELETE` and flags share the bucket) | `429` |
| Writes per source IP | 300 per clock hour (carriers put many phones behind one address) | `429` |
| Reports per install per fountain | 1 per **20 minutes** (the app's own rule is 30; the server is looser so a slow queue never trips it) | `429`, `Retry-After` up to 1200 |
| Reads | no per-caller limit; API Gateway stage throttling only (suggested: 20 req/s steady, 40 burst) | gateway `429` |

The server cap on the note is deliberately more tolerant than the 140-character
limit. Swift counts grapheme clusters; Go would count runes or bytes, and an
ordinary note the app accepted must not be refused for being counted differently
(an emoji sequence is several code points but one character). 140 is a UI limit,
not a wire limit.

Limits are implemented as DynamoDB counter items (section 8.4). Neither the raw
IP nor the raw install token is stored.

**Headers on writes** (`POST`, `DELETE`, flag) whenever the counters were
consulted (so not on a request refused earlier for size or validation),
describing the install bucket:

```
RateLimit-Limit: 40
RateLimit-Remaining: 37
RateLimit-Reset: 1260        (seconds until the hourly window ends)
```

**On `429`** the response also carries `Retry-After: <integer seconds, at least 1>`
and `error.code = "rate_limited"`, with `error.reason` one of `install`, `ip`,
`fountain` so logs say which bucket tripped.

**Order of checks on `POST /v1/reports`** (idempotency comes before the rate
limit, so a retry of a report that already landed is a success, never a 429):

1. Size, content type, `X-Toret-Install`.
2. Validate the body (section 6.4).
3. `GetItem` the report id. Exists with the same install hash: `200` with the
   stored report. Exists with another install hash: `409 id_conflict`.
4. Ban check (`BAN#<installHash>`): `403 forbidden`.
5. Rate-limit counters: install hour, IP hour, install-fountain gate.
6. Conditional `PutItem` (`attribute_not_exists(pk)`). Losing that race to a
   concurrent identical request is treated as step 3's success.

`DELETE /v1/reports/{id}` and `POST /v1/reports/{id}/flag` check, in order:
size and content type (flag only), `X-Toret-Install`, the id (`422 invalid_id`),
the flag body (`400` / `422 invalid_reason`), the ban, the install and IP hourly
buckets, then act. The per-fountain gate applies to `POST /v1/reports` only.

## 5. Caching

| Route | `Cache-Control` | ETag |
| --- | --- | --- |
| `GET /v1/health` | `no-store` | no |
| `GET /v1/reports`, `GET /v1/fountains/{id}/reports` | `no-cache` | yes |
| `GET /v1/summaries` | `private, max-age=60` | yes |
| `GET /v1/conditions` | `public, max-age=300` | yes |
| writes | `no-store` | no |

Lists use `no-cache` (store, but always revalidate) rather than `max-age` on
purpose: `Community.refresh()` calls `flush()` and then `recent()`, and a
`max-age` copy fetched before the POST would not contain the just-saved report.
Because the report is no longer pending, `Community.merge` would read its
absence from a complete download as "deleted on the server" and drop it.

The `ETag` is a strong validator: `"` + first 16 hex characters of the SHA-256 of
the response body + `"`. Bodies therefore contain **no generation time** (use
the `Date` response header), otherwise every response would differ. A matching
`If-None-Match` gets `304`, no body, and the same `ETag` and `Cache-Control`.
The comparison is weak (`W/` prefixes are ignored) and a list of tags or `*` is
accepted. URLSession handles this transparently when the request uses the
default cache policy. Responses of 1 KiB or more are gzipped when
`Accept-Encoding` allows it (API Gateway HTTP APIs do not compress for you); the
`ETag` is that of the uncompressed body and cacheable responses carry
`Vary: Accept-Encoding`.

### 5.1 Read-after-write is eventually consistent

The list queries run on global secondary indexes, which cannot be read
consistently: a report accepted a few hundred milliseconds ago can be missing
from the next list. Two client rules follow, because `merge` treats "absent from
a complete download" as deleted:

- **A report the device saved less than 60 seconds ago is never dropped for
  being absent from a download.**
- **A report the device deleted less than 60 seconds ago is never re-added from
  a download** (the same lag works in reverse: the deleted report can still be
  indexed).

## 6. Endpoints

All examples use real shapes. `isMine` is part of the Swift `Report` Codable
conformance, so the server **always emits `"isMine": false`**, exactly as
`CloudKitBackend` builds its reports; the client works out ownership from the
handle (`Community.isMine`), never from this field.

### 6.1 `GET /v1/health`

Liveness. No authentication, no DynamoDB access.

```json
{ "status": "ok", "version": "1.0.0", "catalogue": 723 }
```

`version` is the deployed server version (set at build time with
`-ldflags -X main.version=`); `catalogue` is the number of fountains
in the embedded catalogue (a quick check that the right file was embedded).

### 6.2 Reading reports

`GET /v1/reports?limit=<n>` is `CommunityBackend.recent(limit:)`. `GET
/v1/fountains/{id}/reports?limit=<n>` is `reports(for:limit:)`.

| Route | `limit` default | `limit` maximum | Window |
| --- | --- | --- | --- |
| `/v1/reports` | 50 | **200** | newest 30 days (`Community.feedWindow`) |
| `/v1/fountains/{id}/reports` | 40 | **100** | newest 30 days |

`limit` must be an integer of at least 1, otherwise `400 invalid_limit`. A larger
value than the maximum is clamped, but **the maxima are not below what the app
asks for** (200 and 40). This is load-bearing: `Community.merge` calls a download
complete when `count < limit` and then discards cached reports it did not see.
A server that silently returned fewer than `limit` reports while more exist would
make the app delete real reports. There is no pagination for that reason.

The window boundary is inclusive: a report dated exactly 30 days ago is still
listed, one second older is not (the cutoff key is `<RFC 3339>#`, and every key
of a report dated at or after that second sorts above it).

Order: newest first by `date`, ties broken by `id` descending. Reports hidden by
flags or by the owner are excluded (they are absent from the indexes). Reports
older than 30 days are excluded by the query itself, because DynamoDB TTL deletes
lazily (section 8.3).

```json
{
  "reports": [
    {
      "id": "7D2B7C54-3F0A-4C5E-8B6D-0E5C6C1B9A10",
      "fountainID": "421310659",
      "state": "running",
      "rating": 5,
      "tags": ["cold", "clean"],
      "note": "Água gelada, sem fila.",
      "date": "2026-10-12T09:41:00Z",
      "author": "Visitante E95596",
      "isMine": false
    }
  ]
}
```

| Field | Swift (`Report`) | Rules |
| --- | --- | --- |
| `id` | `String` | upper-case UUID |
| `fountainID` | `String` | in the catalogue |
| `state` | `WaterState` | `running`, `weak`, `dry`, `unknown` |
| `rating` | `Int?` | 1 to 5, **omitted** when none, never 0 |
| `tags` | `[ReportTag]` | at most 3, unique; `cold`, `clean`, `strongFlow`, `easyToReach`, `shade`, `dirty`, `hardToFind`; `[]` when none |
| `note` | `String` | trimmed; `""` when none (always present) |
| `date` | `Date` | when the person made the report, section 2.3 |
| `author` | `String` | `Visitante XXXXXX`, derived by the server, section 7 |
| `isMine` | `Bool` | always `false` |

`GET /v1/fountains/{id}/reports` returns `404 unknown_fountain` for an id that
is not in the catalogue. A catalogue id with no reports is `200` with `{"reports":[]}`.

### 6.3 `GET /v1/summaries`

What `ToretModel.apply(summaries:)` takes: `[String: CommunitySummary]`, fountain
id to summary. The shape is a JSON object keyed by fountain id, so a client
decodes it straight into that dictionary type once `CommunitySummary` is made
`Codable` (its stored properties already have the right names and types).

```json
{
  "windowHours": 36,
  "summaries": {
    "421310659": {
      "state": "running",
      "latestDate": "2026-10-12T09:41:00Z",
      "average": 4.5,
      "ratingCount": 2,
      "reportCount": 3
    }
  }
}
```

| Field | `CommunitySummary` | Meaning |
| --- | --- | --- |
| `state` | `state` | State of the deciding report, or `unknown` |
| `latestDate` | `latestDate` | Date of the deciding report |
| `average` | `average` | Mean rating in the window, rounded to 2 decimals; omitted when no ratings |
| `ratingCount` | `ratingCount` | Reports with a rating |
| `reportCount` | `reportCount` | Reports in the window |

A fountain with no report in the window is **absent**; the client reads that as
`CommunitySummary.empty`.

**Computation mirrors `CommunitySummary.summarising` exactly**, over the visible
reports whose `date` is within the last 36 hours of the server clock:

1. The deciding report is the newest one whose state is not `unknown`, else the
   newest report overall (a rating-only report cannot reset "running" to
   "unknown").
2. `state` is that report's state, or `unknown` if it is older than 36 hours.
   `latestDate` is returned either way, so the client can expire the state
   against its own clock (`now - latestDate > 36 h` means `unknown`) without
   another request.
3. `average`, `ratingCount`, `reportCount` come from every report in the window.

Three honest caveats, which the client must keep in mind:

- **Window.** The window is exactly the freshness limit, so `average`,
  `ratingCount` and `reportCount` here cover 36 hours, whereas the app computes
  them locally over the 30-day feed. They differ, and a fountain whose last
  report is three days old is absent here although the detail screen still has
  it ("Último relato há 3 dias"). The local computation from downloaded reports
  stays the source of truth wherever reports are on screen; this endpoint
  seeds pins, widgets and notifications before (or without) a feed download.
- **Blocks.** Summaries cannot honour a person's local blocks (those are by
  handle, on the device) and count every report that is not hidden.
- **Cap.** The server reads at most 5000 reports for one aggregate. Beyond that
  it stops (newest first), which at this volume is a flood, not a normal day.

### 6.4 `POST /v1/reports`

`CommunityBackend.save(_:)`. Idempotent by `id`.

```json
{
  "id": "7D2B7C54-3F0A-4C5E-8B6D-0E5C6C1B9A10",
  "fountainID": "421310659",
  "state": "running",
  "rating": 5,
  "tags": ["cold", "clean"],
  "note": "Água gelada, sem fila.",
  "date": "2026-10-12T09:41:00Z"
}
```

Headers: `X-Toret-Install` (required), `X-Toret-Client`. The body is a `Report`
without `author` and `isMine`; if present they are **ignored**. The server never
trusts an author from the client.

| Result | Meaning | Body |
| --- | --- | --- |
| `201` | Stored | the report, as in 6.2 (object, not wrapped) |
| `200` | Same id from the same install already stored: **no-op success**, whatever the body says now | the stored report |
| `409 id_conflict` | Id stored by another install | error |

Validation, in this order (first failure wins; `field` names the culprit):

1. `id`: a UUID, else `422 invalid_id`.
2. `fountainID`: present in the catalogue embedded at build time (copy of
   `Shared/Resources/fountains.json`, 723 entries, every `kind` accepted), else
   `422 unknown_fountain`.
3. `state`: one of the four values, else `422 invalid_state`. Absent counts as `unknown`.
4. `rating`: absent, `null` or 1 to 5, else `422 invalid_rating`. `0` is invalid.
5. Neither a state other than `unknown` nor a rating: `422 empty_report`
   (`ReportDraft` with nothing to say). `state: "unknown"` is valid only together
   with a rating.
6. `tags`: absent or at most 3 unique known values, else `422 invalid_tags`.
7. `note`: trimmed of whitespace and newlines (the stored value is the trimmed one);
   at most 280 code points; no control characters other than
   `\n`; then the content filter below. Else `422 invalid_note` with `reason`
   `too_long`, `control_characters`, `objectionable` or `contains_contact`.
8. `date`: within **30 days in the past** and **10 minutes in the future** of the
   server clock, else `422 invalid_date`. Queued offline reports can be days old;
   an old date is not corrected, it is only bounded. (A report older than 36 h is
   simply stale in every summary.)

**Content filter.** The server ports `NoteFilter` (`Toret/Community/NoteFilter.swift`)
with the same normalisation (fold diacritics and case, then map `0 1 3 4 5 @ $` to
`o i e a s a s`), the same contact regex and the same word list, matched as whole
words. The Swift file is the single source of truth: when it changes, the Go
port and these vectors change in the same commit.

| Note | Verdict |
| --- | --- |
| `Água gelada, sem fila.` | ok |
| `Ligue 011 123 4567` | `contains_contact` |
| `veja www.exemplo.com` | `contains_contact` |
| `fala com @fulano` | `contains_contact` |
| `Fuck this` | `objectionable` |
| `p#ta` | ok (`#` is not in the substitution map; only listed substitutions are undone) |
| `f0da` | ok (not in the word list) |
| `put4` | `objectionable` (`4` becomes `a`, giving `puta`) |
| `Scunthorpe` | ok (whole words only) |

### 6.5 `DELETE /v1/reports/{id}`

`CommunityBackend.delete(reportID:)`. Requires `X-Toret-Install`.

- `204` when the report was deleted **or does not exist** (already gone, never
  arrived, expired). Deleting twice is harmless.
- `403 not_owner` when the stored install hash differs from the caller's.
- `422 invalid_id` when `{id}` is not a UUID.

The delete is a conditional `DeleteItem` on the install hash. Flag items of the
report are left to expire with their TTL.

### 6.6 `POST /v1/reports/{id}/flag`

`CommunityBackend.flag(reportID:reason:)`. Requires `X-Toret-Install`.

```json
{ "reason": "offensive" }
```

`reason` is `offensive`, `spam` or `false` (the three `ReportRow` sends), else
`422 invalid_reason`. Response is always `204`, also when:

- the report does not exist or is already hidden (so the client queue moves on);
- this install already flagged it (a flag is stored once per report and install);
- the caller owns the report (not counted).

**Auto-hide.** A report with **three** distinct flaggers is removed from every
read automatically (section 8.2). To make three throwaway tokens from one phone
not enough, a flag also counts only once per source IP per report. The owner can
override either way, section 9.

### 6.7 `GET /v1/conditions`

Context only: weather and SMAT works notices, both with provenance. Everything
is read from DynamoDB; the API Lambda never calls an upstream.

```json
{
  "weather": {
    "temperatureC": 24.1,
    "apparentTemperatureC": 26.3,
    "relativeHumidityPercent": 48,
    "apparentTemperatureMaxTodayC": 29.5,
    "observedAt": "2026-10-12T13:30:00Z",
    "fetchedAt": "2026-10-12T13:41:12Z",
    "attribution": "Weather data by Open-Meteo.com",
    "licence": "CC BY 4.0",
    "licenceURL": "https://creativecommons.org/licenses/by/4.0/",
    "sourceURL": "https://open-meteo.com/"
  },
  "notices": {
    "enabled": true,
    "fetchedAt": "2026-10-12T13:05:00Z",
    "items": [
      {
        "id": "a1b2c3d4e5f6",
        "kind": "waterWorks",
        "street": "Corso Vittorio Emanuele II",
        "fountainIDs": ["421310659"],
        "match": "street",
        "startedOn": "2026-10-05",
        "plannedEnd": "2026-10-23",
        "source": "SMAT S.p.A., Mappa Cantieri",
        "fetchedAt": "2026-10-12T13:05:00Z"
      }
    ]
  }
}
```

**`weather`**

- `null` when never fetched, or when the cached value is more than 6 hours old
  (the ingest is down; the app shows nothing rather than an old number).
- Otherwise the last fetched value, with `fetchedAt` (when our ingest got it)
  and `observedAt` (Open-Meteo's `current.time`, converted from Europe/Rome to
  UTC). The app shows both the attribution and the time.
- Fields map to Open-Meteo's `current.temperature_2m`, `current.apparent_temperature`,
  `current.relative_humidity_2m` and `daily.apparent_temperature_max[0]`.
  `apparentTemperatureMaxTodayC` is omitted if the daily array was empty.
- `attribution`, `licence`, `licenceURL`, `sourceURL` are constants the server
  sends so the licence text lives in one place. The ingest refreshes at most every
  15 minutes (Open-Meteo's rule).

**`notices`**

- `enabled` mirrors the `SMAT_ENABLED` environment flag (default `false` in the
  template). **When `false`: `{"enabled": false, "items": []}`**, no `fetchedAt`,
  and the app hides the feature entirely.
- When `enabled` is `true`, `fetchedAt` is the last successful ingest (at most
  hourly). If the last success is more than 6 hours old, or there was none,
  `fetchedAt` is omitted and `items` is `[]`: that means **no data**, which the
  app must not present as "no works".
- `kind` is `waterWorks` (an order of the water division, `divisione` =
  `ACQUEDOTTO`) or `fountainWorks` (the order object `FONTANELLE & TORETTI`,
  whichever division lists it). Sewer (`FOGNATURA`) orders and everything else
  are dropped.
- Only orders in Turin are kept: the address must end `, 101xx Torino TO, Italia`.
  The service returns the whole province (about two thirds of the water orders in
  the first capture were in Chivasso, Rosta, Chieri...), and matching those
  against a Turin catalogue would produce false "near <street>" claims. An order
  whose start date is after today (Europe/Rome) is also dropped, because the app
  words it "started <date>".
- `street` is the street part of SMAT's address string, as published (Italian,
  abbreviations and all): `"C.so Francesco Ferrucci"` from
  `"C.so Francesco Ferrucci, 28, 10138 Torino TO, Italia"`. House number, postcode
  and town are not sent. An intersection stays whole: `"Corso Moncalieri & Corso Fiume"`.
- `fountainIDs` are the fountains whose catalogue `street` equals the order's
  street after normalisation (case and accents folded, dots and punctuation
  removed, a leading abbreviation spelled out: `C.so` is `corso`, `V.` is `via`,
  `Str.`/`S.da` are `strada`, `SC` is `strada comunale`, `P.za` is `piazza`); both
  streets of an intersection are tried. `match` is always `"street"` and is there
  so the approximation stays visible in the data. An order that matches nothing is
  kept with `fountainIDs: []`. This is approximate by construction (SMAT publishes
  no coordinates and no fountain id), and the app words it "near <street>", "may
  be affected".
- `startedOn` always present (an order without a valid start date is dropped);
  `plannedEnd` omitted when SMAT gives none or an invalid one.
- `id` is a stable 12-hex-character hash of SMAT's order number (`numero
  d'ordine`), for list identity. Two orders on one street are two notices; an
  order listed twice is one. At most 300 notices are kept, newest start first.
- `source` is always `"SMAT S.p.A., Mappa Cantieri"`. SMAT has no stated
  licence: this is context, with attribution and time, behind a flag.
- There is **no status, state or availability field**, and there never is one.

## 7. Anonymous identity

No accounts. The app creates a random **install token** once, keeps it in the
Keychain and sends it in `X-Toret-Install` on writes.

- **Token**: `UUID().uuidString` (36 characters, upper case). The server treats it
  as an opaque string and **must not normalise it** (case, whitespace): the
  handle below depends on its exact bytes.
- **Handle** (what other people see and what blocking matches on), identical to
  `AuthorHandle.make(from:)`:

  ```
  handle = "Visitante " + upperHex( first 3 bytes of SHA256( UTF8("toret.author." + token) ) )
  ```

  The server computes it from the raw header on every `POST` and stores it as
  `author`. It ignores any `author` in the body.
- **Install hash** (what the server uses to recognise the same install, and the
  only identifier it stores):

  ```
  installHash = lowerHex( HMAC-SHA256( key = pepper, msg = UTF8("toret.install.v1:" + token) ) )
  ```

  `pepper` is the SSM parameter `/toret/pepper` (SecureString), created at
  deploy time, read by the Lambda once per cold start. It is not in the
  repository. **Never rotate it**: every install would lose ownership of its
  reports (delete would answer `403`). If a rotation is ever needed, add a
  `PEPPER_PREVIOUS` fallback for lookups first.
- **IP hash** (rate limiting only, never stored on a report):
  `lowerHex( HMAC-SHA256( pepper, UTF8("toret.ip.v1:" + sourceIP) ) )`, with the
  address from API Gateway's `requestContext.http.sourceIp`.
- The raw token and the raw IP are never written to DynamoDB or the logs.

**The client must use the same token as the handle's seed.** `Community` derives
its own handle with `AuthorHandle.make(from: accountToken ?? installID)`. For the
HTTP backend, `accountToken()` therefore returns the Keychain install token and
`CommunityState.installID` is only a fallback while that backend is not in use.
Otherwise the handle the app expects (`isMine`, the blocked list) and the one the
server derives would differ. On first use, seed the Keychain token with the
existing `CommunityState.installID` so handles already seen by other people do
not change.

## 8. DynamoDB: one table, on demand

Table `toret` (name is a template parameter), `PAY_PER_REQUEST`, partition key
`pk` (S), sort key `sk` (S), TTL attribute `ttl` (N, epoch seconds), point-in-time
recovery on. Two global secondary indexes, both projecting all attributes (items
are about 500 bytes, so no second read is worth saving):

| Index | Partition key | Sort key | Serves |
| --- | --- | --- | --- |
| `gsi1` | `gsi1pk` (S) | `gsi1sk` (S) | the city feed and the summaries |
| `gsi2` | `gsi2pk` (S) | `gsi2sk` (S) | one fountain's reports |

### 8.1 Items

| Item | `pk` | `sk` | Attributes |
| --- | --- | --- | --- |
| Report | `REPORT#<ID>` | `META` | `id`, `fountainID`, `state`, `rating`?, `tags` (list), `note`, `date` (RFC 3339), `createdAt`, `author`, `installHash`, `flagCount` (N, 0), `dateKey`, `fountainKey`, `hidden`?, `hiddenBy`?, `reviewed`?, `gsi1pk`/`gsi1sk`/`gsi2pk`/`gsi2sk` while visible, `ttl` |
| Flag | `REPORT#<ID>` | `FLAG#<installHash>` | `reason`, `createdAt`, `ttl` |
| Flag per IP | `REPORT#<ID>` | `FLAGIP#<ipHash>` | `ttl` |
| Rate counter | `RL#<scope>#<key>#<window>` | `COUNT` | `n` (N), `ttl` |
| Ban | `BAN#<installHash>` | `BAN` | `createdAt`, `note` |
| Weather cache | `CONDITIONS` | `WEATHER` | `temperatureC`, `apparentTemperatureC`, `relativeHumidityPercent`, `apparentTemperatureMaxTodayC`?, `observedAt`, `fetchedAt` |
| SMAT cache | `CONDITIONS` | `SMAT` | `fetchedAt`, `items` (list of notice maps) |

`<ID>` is the upper-case UUID.

### 8.2 Keys of a visible report

```
dateKey     = <date as RFC 3339>#<ID>          e.g. 2026-10-12T09:41:00Z#7D2B7C54-...
fountainKey = FOUNTAIN#<fountainID>
gsi1pk = FEED          gsi1sk = dateKey
gsi2pk = fountainKey   gsi2sk = dateKey
```

- **City feed**: `gsi1`, `gsi1pk = FEED AND gsi1sk > :cutoff`, `ScanIndexForward=false`,
  `Limit = limit`. `:cutoff` is `now - 30 days` as `<RFC 3339>#`; RFC 3339 UTC
  strings of equal length sort chronologically, which is why timestamps are
  whole-second and `Z`.
- **One fountain**: `gsi2`, `gsi2pk = FOUNTAIN#<id> AND gsi2sk > :cutoff`, same options.
- **Summaries**: `gsi1` with cutoff `now - 36 h`, paged to the cap in 6.3,
  aggregated in memory; the result is cached in the warm Lambda for 20 s.
- `FEED` is a single partition. That is far under DynamoDB's per-partition limits
  at this app's volume (hundreds of reports a day).

**Hiding is removing the index keys.** A hidden report keeps its `META` item but
loses `gsi1pk`, `gsi1sk`, `gsi2pk` and `gsi2sk` and gets `hidden = true`,
`hiddenBy = "flags"` or `"owner"`. Both indexes are sparse, so every read
excludes it with no filter expression and `Limit` stays exact (a filter after the
limit would return short pages, which `Community.merge` would mistake for a
complete download). `dateKey` and `fountainKey` stay on the item so it can be
restored.

**Flag write** (one `TransactWriteItems`, retried up to 3 times on a conflict):

1. `GetItem` the report `META` (strongly consistent). Missing or already
   `hidden`, or owned by the caller: stop, answer `204`.
2. Transaction: `Put` the `FLAG#<installHash>` item and the `FLAGIP#<ipHash>`
   item, each with `attribute_not_exists(pk)`, and `Update` `META` with
   `ADD flagCount :1` under the condition `flagCount = :seen AND attribute_not_exists(hidden)`. When
   `:seen + 1 >= 3` and `reviewed` is absent, the same update also does `SET
   hidden = :true, hiddenBy = :flags REMOVE gsi1pk, gsi1sk, gsi2pk, gsi2sk`.
3. If cancelled because a flag item already exists: answer `204` (already
   flagged). If cancelled because `flagCount` moved, the report was hidden, or
   another transaction conflicted: go back to step 1.

`reviewed` is set by the owner when restoring a report (section 9); a reviewed
report is never auto-hidden again.

### 8.3 TTL and the 30-day retention

`ttl = floor(date as epoch) + 30 days` on a report and on its flag items, so a
report disappears 30 days after the moment it describes (the dates accepted by
`POST` start at most 30 days back, so such a report may live for hours only).
DynamoDB deletes expired items **lazily, up to 48 hours late**, so no read relies
on it: every feed query has the `gsi1sk > cutoff` key condition, and the single-item
reads (`GetItem` for idempotency and delete) are harmless on an expired item.
Counters carry their own `ttl` for the same reason, with the window in the key.

### 8.4 Rate-limit counters

Fixed windows, one atomic update each:

```
UpdateItem  pk = RL#INSTALL#<installHash>#<epochHour>   sk = COUNT
  SET #ttl = :windowEndPlusHour  ADD n :1
  ConditionExpression: attribute_not_exists(n) OR n < :limit
```

| Scope | Key | Window | Limit |
| --- | --- | --- | --- |
| `INSTALL` | install hash | clock hour | 40 |
| `IP` | ip hash | clock hour | 300 |
| `FOUNTAIN` | install hash + fountain id | 20 minutes (`epoch / 1200`) | 1 (`POST` only) |

A failed condition is a `429`; `Retry-After` is the seconds left in the window.
`RateLimit-Remaining` is `limit - n` for the install bucket.

### 8.5 Cost and capacity

A `POST` is about 2 reads and 4 writes; a feed read is one query. At the
expected volume the table is a few cents a month; idle, it is zero. The
template sets reserved concurrency on both functions (parameters; `-1` leaves
one unreserved on an account whose limit is too low to reserve) and API Gateway
throttling on the stage, and uses 14-day CloudWatch retention. The roles are
explicit: the API role may use the table, read the pepper parameter and write
to its own log group; the ingest role may only read and write the two
`CONDITIONS` items.

## 9. Moderation runbook (owner, by AWS CLI)

Offline reference; nothing here is run by the build. Set the table name and
region first. Attribute names go through `#` placeholders because several of
them (`date`, `ttl`, `hidden`...) are DynamoDB reserved words:

```sh
export TABLE=toret AWS_REGION=sa-east-1     # default profile
```

**List everything flagged or hidden** (a scan is fine at this size):

```sh
aws dynamodb scan --table-name $TABLE \
  --filter-expression '#sk = :m AND #fc > :z' \
  --expression-attribute-values '{":m":{"S":"META"},":z":{"N":"0"}}' \
  --projection-expression '#id,#f,#a,#n,#d,#fc,#h,#hb' \
  --expression-attribute-names '{"#sk":"sk","#fc":"flagCount","#id":"id","#f":"fountainID","#a":"author","#n":"note","#d":"date","#h":"hidden","#hb":"hiddenBy"}'
```

**Hide a report now** (also what auto-hide does):

```sh
aws dynamodb update-item --table-name $TABLE \
  --key '{"pk":{"S":"REPORT#<ID>"},"sk":{"S":"META"}}' \
  --update-expression 'SET #h = :t, #hb = :o REMOVE #g1p, #g1s, #g2p, #g2s' \
  --expression-attribute-names '{"#h":"hidden","#hb":"hiddenBy","#g1p":"gsi1pk","#g1s":"gsi1sk","#g2p":"gsi2pk","#g2s":"gsi2sk"}' \
  --expression-attribute-values '{":t":{"BOOL":true},":o":{"S":"owner"}}'
```

**Restore a report** (reviewed and fine; it will not be auto-hidden again):

```sh
aws dynamodb update-item --table-name $TABLE \
  --key '{"pk":{"S":"REPORT#<ID>"},"sk":{"S":"META"}}' \
  --update-expression 'SET #g1p = :feed, #g1s = #dk, #g2p = #fk, #g2s = #dk, #fc = :z, #r = :t REMOVE #h, #hb' \
  --expression-attribute-names '{"#g1p":"gsi1pk","#g1s":"gsi1sk","#g2p":"gsi2pk","#g2s":"gsi2sk","#dk":"dateKey","#fk":"fountainKey","#fc":"flagCount","#r":"reviewed","#h":"hidden","#hb":"hiddenBy"}' \
  --expression-attribute-values '{":feed":{"S":"FEED"},":z":{"N":"0"},":t":{"BOOL":true}}'
```

**Delete a report for good:**

```sh
aws dynamodb delete-item --table-name $TABLE \
  --key '{"pk":{"S":"REPORT#<ID>"},"sk":{"S":"META"}}'
```

**Ban an install** (its writes get `403 forbidden`). Read its `installHash` from
any of its reports, then:

```sh
aws dynamodb put-item --table-name $TABLE --item \
  '{"pk":{"S":"BAN#<installHash>"},"sk":{"S":"BAN"},"createdAt":{"S":"2026-10-12T00:00:00Z"},"note":{"S":"spam"}}'
```

Unban: `delete-item` on the same key. To hide everything from that install, scan
for `#ih = :h` (`{"#ih":"installHash"}`) on `META` items and apply "hide" to each.
A banned install can still read; its `POST`, `DELETE` and flag calls answer
`403 forbidden`.

**Turn SMAT on or off** is a function environment variable (`SMAT_ENABLED`) set
through the template parameter and a redeploy, not a table edit.
